# Enterprise Tax Co-Pilot — Final Scope (Feature Summary ฉบับยืนยัน)
## เวอร์ชันหลังปรับสโคปรอบล่าสุด — เจ้าหน้าที่กรมสรรพากรใช้งาน (Officer / Senior Officer / Admin)

**สถานะเอกสาร**: Final Scope สำหรับเริ่ม implement — แทนที่เวอร์ชันก่อนหน้าทั้งหมด

# ส่วนที่ 0: ข้อกำหนดร่วมของทั้งระบบ (Global Requirements) — เพิ่มใหม่

## 0.1 Authentication & Role-Based Access Control
**ต้องยืนยันสิทธิ์ก่อนเข้าระบบเสมอ** ไม่มีการใช้งานแบบ anonymous — แบ่ง 3 บทบาท:

| Role | สิทธิ์การใช้งาน |
|---|---|
| **เจ้าหน้าที่ (Officer)** | ใช้หน้า Chatbot ถาม-ตอบ, ดูประวัติคำถามของตัวเอง |
| **เจ้าหน้าที่รุ่นพี่ (Senior Officer)** | สิทธิ์เหมือน Officer + อนุมัติ/แก้ไขคำตอบในคิว escalation |
| **ผู้ดูแลระบบ (Admin)** | สิทธิ์เหมือนรุ่นพี่ + เข้าหน้า Admin Dashboard + อนุมัติความรู้ใหม่เข้าระบบ (A5, C4) |

**กระทบต่อ DB Schema**: ต้องเพิ่มระบบ login/session และ field `role` ใน `staff_users` (มีอยู่แล้วบางส่วนใน schema เดิม แต่ต้องเพิ่ม authentication layer จริง เช่น password hash, session token)

## 0.2 โครงสร้างหน้าจอ 2 ส่วนหลัก

### ส่วนที่ 1: Chatbot Interface (สำหรับเจ้าหน้าที่ทุกคน)
หน้าจอแบ่ง **3 คอลัมน์**:
- **ซ้าย**: ประวัติคำถามที่เคยถาม (ของผู้ใช้คนนั้น)
- **กลาง**: หน้าจอถาม-ตอบหลัก (chat interface)
- **ขวา**: ต้นฉบับประกาศ/กฎหมายเต็ม พร้อม highlight ข้อมูลที่ถูกอ้างอิง (เหมือน Feature A1 เดิม)

### ส่วนที่ 2: Admin Dashboard (สำหรับ Admin/รุ่นพี่เท่านั้น)
แสดงข้อมูลสรุปการใช้งานทั้งหมด: คำถามที่พบบ่อย (แยก in-scope/out-of-scope), log การถาม-ตอบทั้งหมด, กราฟ Heatmap พื้นที่/หัวข้อที่ถูกถามบ่อย

## A2. Out-of-Scope Router — 🔄 แก้ไข (เพิ่มความเข้มงวด)

**สเปคใหม่**:
1. ตรวจสอบ **intent ที่แท้จริง** ของคำถาม โดยใช้ **ทั้ง 2 วิธีร่วมกันเสมอ**: (ก) match กับตาราง keyword/taxonomy และ (ข) เทียบผลจาก LLM — ไม่ใช้วิธีใดวิธีหนึ่งเพียงอย่างเดียวอีกต่อไป
2. ตรวจสอบว่าอยู่ในสโคป VAT Registration หรือไม่ จากผลลัพธ์ทั้ง 2 วิธีประกอบกัน
3. ถ้าไม่ตรงสโคป → แจ้งหน่วยงานที่ต้องติดต่อ (เหมือนเดิม)

**ความแตกต่างจากสเปคเดิม**: เดิมออกแบบเป็น "keyword-first, LLM fallback เฉพาะเมื่อ keyword จับไม่ได้" (เพื่อประหยัด resource) แต่ตอนนี้ **ต้องเช็คด้วย LLM ควบคู่กับ keyword ทุกครั้ง** เพื่อความแม่นยำ

**เหตุผลที่ user ให้ไว้**: ป้องกัน intent ที่ตีความผิดพลาดจากการพึ่ง keyword เพียงอย่างเดียว

**⚠️ Trade-off ใหม่**: ใช้ LLM call ทุกคำถาม (ไม่ประหยัด compute เท่าที่ออกแบบไว้เดิม) — ต้องพิจารณาผลกระทบต่อ latency และ RAM budget ที่วิเคราะห์ไว้ในเอกสาร Optimization Comparative Analysis ใหม่อีกครั้ง (เดิมประเมินไว้บนสมมติฐาน keyword-first ประหยัด LLM call)

**🔧 ต้องเตรียม**: ตาราง `departments` + keyword ครบ, ปรับ prompt LLM ให้ตอบเร็ว/สั้นที่สุด (เช่น ตอบแค่ scope label ไม่ต้องมี reasoning ยาว) เพื่อลดผลกระทบต่อ latency

---

## A3. Dynamic Checklist Assistant — 🔄 แก้ไข (เปลี่ยนรูปแบบการทำงาน)

**สเปคใหม่**:
1. ระบบเก็บ **คุณสมบัติของผู้ขอจดทะเบียน** (entity type, สถานการณ์พิเศษ ฯลฯ) ผ่านการสนทนา/กรอกข้อมูล
2. นำคุณสมบัติเหล่านั้นมาสร้างเป็น **Checklist Assistant**
3. **เจ้าหน้าที่เป็นผู้ทำเครื่องหมาย (check off)** เอกสารที่ได้รับแล้วเอง (ไม่ใช่ AI generate checklist แล้วจบ)
4. ระบบสรุปให้ว่า **เอกสารอะไรยังขาดอยู่บ้าง**

**ความแตกต่างจากสเปคเดิม**: เดิมเป็น guided interview ที่ AI ถามคำถามนำไปสู่ checklist อัตโนมัติทั้งหมด ตอนนี้เปลี่ยนเป็น **Human-in-the-loop แบบ manual checklist ที่เจ้าหน้าที่ควบคุมเอง** AI มีหน้าที่แค่ (ก) เก็บคุณสมบัติ (ข) generate รายการเอกสารที่ควรมี (ค) สรุปส่วนที่ขาด — ไม่ใช่ตัดสินใจแทนเจ้าหน้าที่

**เหตุผลที่ดี**: ลดความเสี่ยงที่ AI จะ "ปิด" checklist เองโดยไม่มีเจ้าหน้าที่ยืนยันว่าได้รับเอกสารจริง — accountability อยู่ที่เจ้าหน้าที่เสมอ

**⚠️ Trade-off**: ยังต้องพึ่ง case library/decision tree ที่ครอบคลุมเพื่อสร้างรายการเอกสารเริ่มต้นที่ถูกต้อง

**🔧 ต้องเตรียม**: ออกแบบ UI checklist แบบ checkbox ที่ใช้งานง่าย, schema เก็บสถานะ "ได้รับแล้ว/ยังขาด" ต่อเอกสารต่อเคส (เพิ่มตารางใหม่ เช่น `document_checklist_items`)

---

## A4. Risk-Based Escalation & Supervisor Approval — ✅ ไม่แก้ไข (ย้ำหลักการเดิม)

**ยืนยันชัดเจน**: คำนวณคะแนนความเสี่ยงด้วย **Rule-based เท่านั้น** — **LLM ห้ามคิดคะแนนเอง** (ตรงกับที่ AI-1/AI-2/AI-3 ในรายงานเปรียบเทียบเห็นตรงกันหมด — เป็นฉันทามติที่ user ยืนยันอีกครั้ง)

---

## A5. Internal Ruling & Precedent Search — 🔄 แก้ไข (เข้มงวดขึ้นมาก — สำคัญที่สุด)

**สเปคใหม่ (ยึดหลัก Deterministic & Verifiable)**:
1. ตอบโดย**อ้างอิงจากประกาศและข้อหารือที่มีหลักฐานเท่านั้น** (official announcements + verified rulings)
2. **ในเบื้องต้นตอบได้เฉพาะจากเอกสารที่ใส่ให้ระบบเท่านั้น** (ingested documents) — ไม่ใช้ความรู้ทั่วไปของ LLM
3. **ห้ามนำ "ประสบการณ์" ของเจ้าหน้าที่มาผสมกับคำตอบ** ยกเว้นได้รับอนุมัติจากผู้ดูแลระบบเท่านั้น (ต้องผ่าน Admin approve ก่อนถึงจะถูกนำมาใช้เป็นแหล่งอ้างอิงได้)
4. **หลักการ Consistency**: ถ้าถามคำถามเดียวกัน → ต้องได้คำตอบเดียวกันเสมอ (ไม่ใช่คำตอบเปลี่ยนไปมาแต่ละครั้งที่ถาม)

**ความแตกต่างจากสเปคเดิม**: เดิมออกแบบให้ index ทั้งตัวบทกฎหมายสาธารณะ + แนวปฏิบัติภายใน (รวมประสบการณ์เจ้าหน้าที่) มารวมกัน ตอนนี้ **แยกชั้นความน่าเชื่อถือชัดเจน**: (ก) เอกสารทางการที่ ingest ไว้แล้ว = ตอบได้ทันที (ข) ความรู้จากประสบการณ์ = ต้องผ่าน Admin อนุมัติก่อนถึงจะเข้าสู่ knowledge base ได้ (เชื่อมกับ Feature C4 Knowledge Growth Loop โดยตรง — Admin approve = จุดเดียวกัน)

**เหตุผลสำคัญมาก**: ป้องกัน "คำตอบไม่คงที่" ซึ่งเป็นปัญหาที่อาจารย์กังวลตั้งแต่ต้น (เจ้าหน้าที่ตอบไม่ตรงกัน) — ฟีเจอร์นี้แก้ปัญหานั้นได้จริงด้วยการบังคับ single-source-of-truth และ deterministic behavior

**⚠️ Trade-off**: ช่วงแรกฐานความรู้จะ "แคบ" เพราะตอบได้แค่จากเอกสารที่ ingest ไว้ ถ้าเอกสารไม่ครอบคลุมเคสจริง ระบบจะต้อง escalate บ่อยกว่าที่ควร (แต่ถือเป็น trade-off ที่ยอมรับได้เพื่อความน่าเชื่อถือ)

**🔧 ต้องเตรียม**:
- แหล่งประกาศ/ข้อหารือที่มีหลักฐานยืนยัน (จากกรมสรรพากรจริง ไม่ใช่สรุปจากที่อื่น)
- กระบวนการ Admin Approval สำหรับนำ "ความรู้จากประสบการณ์" เข้าระบบ (workflow แยกจาก KB Growth ปกติ หรือรวมเป็น pipeline เดียวกัน)
- กลไกยืนยัน consistency (เช่น cache คำตอบต่อคำถามที่เคย approve แล้ว แทนการ generate ใหม่ทุกครั้งสำหรับคำถามที่ตรงกันเป๊ะ)

## C2. Peer Case Frequency → เปลี่ยนเป็น "รายงานคำถามยอดนิยม" 🔄 แก้ไข (เปลี่ยนรูปแบบทั้งหมด)

**สเปคใหม่**:
- **เปลี่ยนจาก** ข้อความเสริมท้ายคำตอบแบบ real-time (inline hint) **เป็น** รายงานสรุปที่แสดงว่า **แต่ละสัปดาห์มีคำถามที่เจอบ่อยคืออะไร**
- ผู้ใช้ (เจ้าหน้าที่) เห็นเป็นรายงานสรุป ไม่ใช่ inline text ต่อคำถาม
- **ผู้ดูแลระบบเห็นข้อมูลในวันทำการถัดไป** (batch ประมวลผลตอนกลางคืน วันละ 1 ครั้ง — ไม่ real-time)

**ความแตกต่างจากสเปคเดิม**: เดิมเป็น real-time inline hint ต่อท้ายทุกคำตอบ ตอนนี้เปลี่ยนเป็น **รายงานสรุปแบบ batch** ที่แยกออกจาก flow การตอบคำถามโดยสิ้นเชิง — ลดความซับซ้อนของ Agent 7 (Chat pipeline) และย้ายภาระไปที่ batch job แทน

**🔧 ต้องเตรียม**: batch job รันตอนกลางคืน (คล้าย pattern ของ C4 Knowledge Growth) สรุปคำถามยอดนิยมรายสัปดาห์ ให้แสดงในหน้า Admin Dashboard

---

## C3. Reasoning Trace Mode → เปลี่ยนเป็น "FAQ / คู่มือความรู้ Generator" 🔄 แก้ไข (เปลี่ยนวัตถุประสงค์)

**สเปคใหม่**:
- **ตัดโหมด** "แสดงว่า AI คิดอะไร" (reasoning trace) ออกทั้งหมด
- **แทนที่ด้วย**: นำข้อมูลคำถาม-คำตอบทั้งหมดไปสรุปเป็น **คำถามยอดนิยม** ใช้สำหรับ**จัดทำคู่มือความรู้ (Knowledge Manual)** ให้เจ้าหน้าที่ทั้งเก่าและใหม่

**ความแตกต่างจากสเปคเดิม**: เดิมเป็นเครื่องมือสอน "วิธีคิด" ของ AI แบบ interactive (technical, real-time) ตอนนี้เปลี่ยนเป็น **เครื่องมือสร้างเอกสารความรู้แบบ static** (เหมาะกับ onboarding และการทบทวนความรู้มากกว่า ไม่ต้องเข้าใจกลไก AI เลย)

**เหตุผลที่ดี**: เข้าถึงง่ายกว่าสำหรับเจ้าหน้าที่ทุกระดับ ไม่ต้องมีพื้นฐาน AI/technical ก็ใช้ประโยชน์ได้ และผลลัพธ์ (คู่มือ) นำไปใช้นอกระบบได้ด้วย (พิมพ์แจก, ใช้ฝึกอบรม)

**🔧 ต้องเตรียม**: เชื่อมกับ batch job เดียวกับ C2 (ใช้ข้อมูลชุดเดียวกันได้), ออกแบบ template คู่มือความรู้ที่ export เป็นเอกสารได้ (เช่น PDF/Word)
